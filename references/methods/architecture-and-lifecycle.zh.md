# 包、组合、启动与边界


本节是综合方法的一页：解释包、组合、启动与边界这一变更面；逐项来源与覆盖见[来源与覆盖](sources-and-coverage.zh.md)。

依赖声明是对“安装后能否运行”的承诺。工作区提升（hoisting）会让漏声明的包在 monorepo 内暂时可用，独立打包或换包管理器后才失败；所以跨包导入必须用包名，manifest 的依赖段要覆盖源码实际使用。可选依赖的承诺更强：未安装时包仍能加载并给出清晰行为，因此发布源码中不能有静态值导入；只用于类型时改为 `import type`，真正需要运行时值就放到函数或生命周期边界，并由调用方处理缺失。动态 `import()` 只适合“确实需要该包并会处理缺失”的调用方，不能作为绕过静态检查的默认手段。

产品组合规则解决的是“代码存在但没有任何入口使用它”以及“实验代码漏进默认安装”。新增官方包要么被默认/可选组合可达，要么在维护者清单中写明类别与理由；过期分类必须删除。实验包不能进入默认依赖图、默认配置或默认源码导入；若要“随产品安装但默认关闭”，只能作为可选组合，并补齐插件管理器需要的 patch、图标和展示资源。启动路径也必须收敛：插件树由一个受支持的入口组合定义，不能同时维护两套并行 bootstrap。配置里写下的插件名必须由拥有 manifest 解析；部署可调参数是经验证的 Config 字段，而不是模块常量。配置键、资源和凭据各有 owner；shipped 配置只引用环境变量名或由 adapter 解析端点，不把 `!!js` 凭据内联进 bundle，否则会绕过凭据解析阶梯。

运行期边界集中在扩展点、生命周期和错误路径。新能力通过已有服务/扩展点接入，新 Context 属性由注册方声明、消费方注入，而不是在核心循环里散落业务分支；确需修改 agent-loop 时同步架构文档。注册是 effect：返回 disposer 或规定的清理句柄，卸载或 HMR 时撤销贡献。资源清理必须等有 owner 且可观察的消费者真正结束，再释放其依赖；仅发出 abort/kill 不等于静止，清理完成前所需监听器与持久化通道也不能提前移除。没有 owner 可等待的 detached 工作是该条明确边界，不把它扩写成能等待所有后台行为。waterfall 的 `next()` 是另一项独立的委派语义：想继续链条必须调用，直接返回才短路，不能把短路本身当作任务已停止的证明。配置错误尽早可读地失败，运行失败有处理者和可见报告，空 `catch` 说明忽略原因。

浏览器侧有两条独立边界。Host 与 Client 使用显式编译面，浏览器代码不导入 Host-only 依赖；双面包分别暴露各面的叶配置，根仅作 solution，聚合程序引用具体面而非混合根。浏览器请求和资源 URL 相对当前文档解析，才能在子路径或反向代理后保持正确；内部路由注册键可以是绝对 pathname，但不因此把发出的请求写成根绝对地址。业务 HTTP 调用不构造 undici Agent 或覆盖 fetch dispatcher 绕过用户代理；确需独立传输时声明理由并使用代理感知机制。vendor 更新记录固定上游版本、本地修改与重放步骤，升级后重新应用或明确移除补丁，并完成规定的测试和构建。

| 原条 | 触发与义务 | 失败机制与责任 | 验证、例外与迁移边界 |
|---|---|---|---|
| 2.01 依赖显式声明 | 跨包 import 或依赖变化时，包名、目录、workspace 范围和 manifest 依赖段与用途一致；运行依赖完整声明，跨包用包名导入。 | workspace 提升掩盖缺声明，安装后找不到。包 owner 负责。 | constraints、依赖/路径/运行闭包检查；触达分发解析风险时补真实安装证据。静态扫描不证明任意动态加载，不能把源码绿当安装绿，也不默认每次全量打包。 |
| 2.02 可选依赖不能静态加载 | 包声明为 `optionalDependencies` 或 optional peer 时，发布源码的静态值导入为零；类型用 `import type`，值使用放在处理缺失的边界。 | 未安装时模块加载即崩，optional 承诺失效。包 owner 与调用方共同负责降级。 | `verify-optional-dependency-imports`；再用 packed install 分别测试安装/不安装。动态导入不是默认答案；打包器内联也需检查 external。 |
| 2.03 官方包要有产品用途或分类 | 新增非实验包时，要么被默认/可选产品组合可达，要么写明确类别与理由；stale 分类删除；实验包保持在默认安装、运行导入和组合之外，声明的可选 bundle 例外按规则处理。 | 包长期无入口，或为逃避检查被挪进 experimental 改变发布面。产品组合 owner 负责。 | `verify-product-use`、`verify-default-product-isolation`、`gen-official-bundle-catalog --check` 加实际入口验证。源仓的 profile/bundle 与类别值是特定实现，不能照搬；静态分析看不到任意字符串/服务发现加载。 |
| 2.04 启动入口唯一 | 新增/修改启动方式时，受支持 Node 应用由单一入口定义插件树；不新增绕过它的 package bin、demo 或公共 SDK argv 入口。 | 两套入口加载不同插件，行为分叉。启动 owner 负责组合定义。 | `verify-application-entrypoints` 加真实启动 smoke。源仓用 dsh profiles 表达组合；“唯一”指组合定义唯一，不是只能有一个命令或一个配置文件。 |
| 2.05 配置与参数有明确 owner | 修改 `cordis.yml`、overlay、插件配置或 resolver manifest 时：裸插件名必须在拥有 manifest 的 dependencies 中；部署可调参数是经验证的 Config 字段；shipped 配置不内联凭据/端点。 | 配置里写了名字但运行时无法解析；模块常量让用户无法按部署调整；内联凭据绕过解析阶梯。配置 owner、resolver owner 与 adapter owner 负责。 | `verify-cordis-config`、`verify-config-source-ownership` 加评审 Config 设计；后者是窄检查，只覆盖单行内联形式，不证明所有键单一来源，运行时注入另测。 |
| 2.06 新能力走扩展点 | 新功能/替换核心实现优先通过既有 Service Definition、Provider、Consumer 扩展点或事件注册；新 Context 属性归注册方，消费方注入；确需修改 agent-loop 时同步架构文档。 | 到处修改核心循环，替换实现时牵一发动全身。功能 owner 与核心 owner 共同评审。 | 评审扩展图、架构文档与卸载测试。局部内聚逻辑可直接修改，不必为插件化而插件化；关键看是否增加第二套控制流。 |
| 2.07 注册要可卸载 | 注册服务、事件、listener、HMR 副作用时通过 `ctx.effect()`/`ctx.on()` 管理，返回 disposer 或文档规定的清理句柄；所有权单一，重载不重复注册。 | HMR 后 listener 累积，关闭时泄漏。注册 owner 负责释放。 | 生命周期/unload 测试加 HMR 场景。源仓有具体 HMR 测试；目标没有 HMR 时仍需等价关停测试，或明确记录缺口。 |
| 2.08 先结束使用者，再释放资源 | 后台任务、子进程和共享状态有 owner；清理等待消费者实际结束，再关闭其使用的服务与完成通道。 | 仅请求终止就释放资源，消费者继续访问已关闭对象。资源与任务 owner 负责顺序。 | 生命周期与失败路径验证观察 settle → release，不能只断言调用了 close/abort；无 owner 可等待的 detached 工作是源条款的边界。 |
| 2.09 waterfall 委派必须调用 next | 增加/修改 waterfall listener 时，想继续处理必须调用 `next()`；直接返回是短路，只在确实想结束处理时使用。 | 日志类 listener 忘记 `next()`，后续真正处理器不运行，行为像被吞掉。listener 作者与事件 owner 负责。 | 评审加链式处理测试。分派模式是事件契约的一部分；不能把普通广播事件当成 waterfall，反之亦然。 |
| 2.10 错误配置和失败不能静默消失 | 配置问题在加载期或最早可解析点失败；运行失败有处理者和用户可见报告；空 `catch` 说明忽略原因。 | 继续执行把最初错误变成更晚、更难定位的错误，或使用不可信结果。加载器/handler owner 负责。 | 评审加失败路径测试。源仓错误类型/报告通道是特定实现；关键是失败可见、有 owner，不把日志当恢复。 |
| 2.11 Host/Client 编译面明确 | 客户端不导入 Host-only 依赖，包与领域依赖图保持明确；双面包使用 face-specific 叶配置与 solution-only 根。 | 混合程序产生声明冲突，浏览器 bundle 引入 Node 能力。包与编译面 owner 负责。 | 客户端包/领域图检查及受影响编译、构建；目标没有对应面时按实际模块边界判断，不为照搬而制造 Host/Client 拆分。 |
| 2.12 浏览器请求用相对 URL | 浏览器请求/静态资源使用文档相对地址，经客户端路由解析；内部路由注册键可以保留绝对 pathname；子路径部署与代理下仍正确。 | 绝对 `/api` 绕过 proxy base，部署到前缀后 404。client owner 负责。 | `verify-client-route-resolution` 加子路径/代理 smoke。只测根路径不能证明；没有该脚本时用实际代理部署验证。 |
| 2.13 代理配置不能绕过 | HTTP transport 的代理、证书、超时由单一 owner 管理；业务代码不构造 Agent 或覆盖 global dispatcher；确需独立 transport 时声明理由并使用代理感知机制。 | 某调用绕过代理/证书策略，生产环境行为不一致。transport owner 负责。 | `verify-no-bare-dispatcher` 加代理集成测试。目标不使用 Node/undici 时映射为“唯一 transport 配置入口”；不能因缺脚本判不适用。 |
| 2.14 vendor 记录来源和本地修改 | 引入/升级 vendored 代码时记录固定上游版本/commit、本地修改与 sync 步骤；升级后重新应用或明确移除本地修改，并更新 manifest。 | 升级覆盖本地补丁，或无法追溯当前代码来源。vendor owner 负责。 | `check-vendor-manifest`、`rescope-vendor:check` 加 sync 后 build/test。没有 vendor 目录则不触发；有 vendor 但缺账本仍是治理缺口，不是“无义务”。 |
