# 评审、合并与历史改写：让判断、权限和证据对得上（7.01–7.11）


本节是综合方法的一页：解释范围、评审、合并、权限与证据失效这一变更面；逐项来源与覆盖见[来源与覆盖](sources-and-coverage.zh.md)。

**一、PR 描述要对应当前改动，Issue 与标签要能说明为什么评审。** 可核实的描述义务来自现有 PR 模板：Motivation 说明要解决的问题并引用同仓库 Issue，Changes 说明命令、配置、API、协议或持久化变化与用户/模型/系统可观察行为，Testing 为每种验证方法列一条并把可复核证据放进 Proof。作者只写实际执行过的验证，处理 review 或改变范围后更新描述；只跑一个测试文件却写“全部测试通过”会把风险藏起来。源材料另称存在 `dsh-pr-description` 技能与 AI 使用披露要求，但固定提交的 19 个技能目录中没有该技能，PR 模板也没有披露栏；这部分是未核实内容，不能作为强制义务。若目标要求披露 AI 参与，应作为项目自定政策明确写进模板，而不是声称源已强制（7.01）。适用的 PR 必须引用至少一个本仓库 Issue，PR 编号（包括栈依赖 PR）不算 Issue；恰好一个允许的 `kind/*`、至少一个 `area/*`、最多一个 p0–p3。强制范围是“非草稿、人工作者、且已有 review request 或已提交 review”；Draft、Bot/App 与尚无 review 请求的 PR 豁免，豁免不解析引用也不读 Project。解决型引用（Fixes/Closes/Resolves）才读取 Project Priority，普通 `Refs` 只建立上下文；PR 关闭多个 Issue 时 Priority 要符合其中最高优先级，缺少必需 Project 访问应失败而不是静默跳过（7.02、7.03）。

**二、审批要同时满足分数与无阻塞意见，委派不能凭空增加分数。** 源策略要求加权 approval 达到阈值且没有有写权限评审人的有效 `CHANGES_REQUESTED`；草稿保持 `pending`，作者自己的 review 不计分，read-only 或失去权限的账号不计入，评分或依赖准备失败才是 `error`。默认 2 分、普通审批 1 分是源参数，目标应设自己的阈值与权重。源还按作者历史合并数与生产代码归属行给加权；作者 credit 不能单独满足阈值，归属加权可以把一份普通审批提高到阈值。这些公式与固定权重按目标政策定义，不能当作通用数值。还要区分两个信号：承担状态写入的 publisher job 成功，只说明评估与发布完成；合并规则应要求 `weighted approval` 这个 commit status，并指定 expected source 为 GitHub Actions，否则任何有 `statuses: write` 的集成都能发同名 `success`。`/delegate @user` 必须是 PR 会话评论的全部文本；双方当前都要有 write/admin 且都不是 PR 作者；每位发送者最多贡献一次，发送者最新有效命令按创建顺序生效，旧命令编辑不会提高优先级；他人编辑过的评论不能转移原作者权重。委托后发送者自己提交任何 review（含仅评论）会收回分数，被委托人的审批被撤销或替换则计分消失，但被委托的点不能再次转发。上述由审批策略测试与工作流测试覆盖，线上 branch rule 与 App 权限仍属平台配置（7.04、7.05）。

**三、写合并状态的工作流要用可信代码，本地按 diff 选证据，失败不能写成通过。** 源审批与 Issue 策略 checkout 默认分支的程序与配置，PR 文件只作为数据读取，不执行；读取或计算出错应发布失败/错误状态，不能留下旧的成功。源还有一个实际限制：checkout 或第一次 `pending` 状态写入本身失败时，末尾的 `error` 步骤不会执行，同一 head 的旧 `success` 可能保留；迁移时应让状态写入失败本身可观测，不能把源描述成完全 fail closed。这里的信任边界必须说准：`issue-policy.yml` 使用 `pull_request`，因此不保证**工作流 YAML 本身不受 PR 改动影响**；源只保证检出的 Node 策略代码来自默认分支。要更强边界，目标须另行设计并验证受保护的工作流及状态来源，不能宣称源已保证。本地推送前按 live base 的完整 diff 选择最小充分证据；源钩子是刻意窄的：pre-commit 只做暂存 lint 修复、空白检查、翻译配对、归档 Note 与 vendor/provider 元数据守卫，pre-push 只跑增量 typecheck，CI 拥有穷尽矩阵。因此不能假定 hook 已测行为、文档、快照或产物，也不因提交或推送重复已通过且未失效的检查。相关检查失败就修复或报告阻塞；CI pending 如实标注 pending；环境问题要给出具体命令、失败测试与平台差异，不能只说“应该是 CI 的问题”；缺少凭据的自跳过等同未验证，hook 绕过只在用户明确授权时发生（7.06、7.07、7.08）。

**四、重写历史要精确 lease，依赖 PR 用官方 stack，检查系统本身也要有顺序与测试。** 重写后的分支发布前先 fetch 并记录远端确切 OID，用 `--force-with-lease=<branch>:<observed-oid>` 发布；远端移动则中止，禁止裸 `--force`。官方 stack 工具为其管理分支提供 lease 保护；重写后要重新获取 head，重审未解决 review、审批、可合并性与检查，旧提交哈希与行内评论锚点不再当前。同仓库依赖链应使用官方 stacked PR，而不是逐个 merge/retarget 模拟；`gh stack sync` 可能先级联 rebase 并推送再给本地验证机会，这是“先发布、立即验证”的专门例外：同步后要重新查询 stack 顺序与各层 head，对每个受影响层运行所选证据，全部通过前不合并；失败时保留 lease 保护的头、修复并发布更正，不能因命令成功就声称栈已就绪。检查系统自身也要满足执行顺序：启动子进程前校验 gate 图依赖，读产物前先构建，共享产物的写入不能与读取并发，聚合检查必须确认每个必需 job 成功并拒绝 `skipped`。一个 Web 热更新测试重写 `lib` 时，不能与仍在读 `lib` 的检查任意并行；聚合遗漏一个 blocking job 或把漏跑当成功，会制造假绿（7.09、7.10、7.11）。
