# 项目结构：目录、模块、依赖与演进

建立项目、放置新代码、拆分或迁移模块、改变依赖和构建布局时使用本页。它是[项目标准](project-standard.md#project-standard)的结构规范，不是建议目录集。目标是让开发者从实际目录和架构地图确定：一项能力由谁拥有，代码放哪里，允许依赖谁，通过什么入口装配，怎样验证和退出旧结构。

本页拥有代码目录、包内组织和结构变更的执行约定，以 deepseek-harness 的实际布局为起点，不另造可任选的目录体系。文档分层由[文档放置](documentation-structure-and-prose.md#tier-placement)及[建立/改造的事实归属](documentation-adoption-and-checks.md#migration)拥有，决策目录与生命周期由[Agent Notes](agent-notes.md#1-激活与目录)和[决策治理](decisions.md#lifecycle-classification)拥有；本页只链接，不复制其分类表或生命周期正文。来源的业务能力名、Cordis实现和语言配置不冒充所有目标项目的产品功能。

<a id="structure-map"></a>
## 1. 每个项目维护一张真实结构地图

固定入口为 `docs/architecture.md`，根 `AGENTS.md` 和 `docs/development.md` 链接它。已有架构正文迁入或按职责拆到它所链接的下层拥有者，不保留第二份同权威地图。小项目可以是一页短表，但必须包含以下实际内容：

- **目录职责与定位。** 实际源码根、业务/能力模块分组、应用或库的公开入口、测试及夹具、开发工具、配置、生成源与产物的位置；存在的 vendor、实验内容、运行数据和维护状态分别归谁。不要求不存在的类别创建空目录。
- **模块与依赖方向。** 说明能力族及允许的依赖方向，链接组README中的直属包地图和包README中的合同；包含运行环境或编译面隔离（如浏览器与服务端）以及共享层约束。详细类型、导出和依赖声明归其实现、manifest与生成图，不在架构页另抄一份包清单；生成图同时链接其生成/检查入口。
- **装配与新增行为落点。** 用户入口怎样调用/组合模块；新增同类功能应该加入哪个模块、注册点或配置。共享状态和资源的生命周期由谁管理。无插件机制也要写清函数调用或构造装配点，不为了地图制造插件框架。

架构页拥有组成和关系，不接管接口类型、实现细节、长期理由或任务状态。模块说明拥有自身合同；复杂子系统另有类型/语义owner，架构页只链接。修改关系的同一变更必须更新地图和受影响说明，不能等积累到失真后再补。

**完成条件：** 给出当前一项真实功能，开发者能沿地图找到入口、拥有模块、依赖和验证位置；给出下一项同类功能，能确定放置位置及允许的依赖，而不是只看见目录树。

<a id="structure-placement"></a>
## 2. 以来源实际布局建立代码目录

来源不是“自己选一种合理目录”，而是应用与能力包分开、能力包固定归组、每层有自己的直属地图。下列是来源代码布局的角色与路径，不是另造的业务样例；同类包和语言专用文件未全部展开：

```text
apps/<app>/                         应用入口与产品装配
packages/
  README.md                         能力族总地图
  <group>/
    README.md                       本能力族的直属包地图
    <package>/
      src/                          产品实现
      tests/                        包级测试与局部夹具
      package.json                  依赖、公开入口与发布内容
      tsconfig.json                 源仓TypeScript编译配置
      README.md                     本包合同
      README.zh.md                  中文对侧
      README.i18n.yaml              双语配对记录
scripts/                            仓库检查、生成与编排
snapshots/                          会话驱动的产品行为快照
benchmarks/                         性能基准与门禁
vendor/                             固定来源的第三方源码
native/                             原生模块
python/                             Python SDK与运行时分发
website/                            文档网站投影
```

**应用、能力族和包。** 来源用 `apps/*` 收集产品应用，用 `packages/*/*` 收集能力包；例如文件系统族的 `fs` 定义服务、`fs-local` 提供本地实现、`tool-fs` 提供模型工具。目标替换的是实际业务能力名，不是取消这层组织。每个包恰属一个能力族，新增包先找已有族；新族必须有职责、直属README并更新 `packages/README.md`。具体包深度、组目录不得带manifest等约束由[包形态](engineering-module-surfaces.md#engineering-package-shape-exports)拥有，不在本页另设检查版本。

**包内组织。** 源码放包内 `src/`，测试和局部夹具放包级 `tests/`，不是 `test/`、`src/__tests__/`，也不默认汇总到根测试杂物箱。共享测试基础设施在 `packages/test-support/`，跨包集成测试归实际组合拥有者。`src/types.ts` 若存在只放类型；构建产物和Host/Client编译面按[源码与产物平面](engineering-module-surfaces.md#engineering-source-artifact-plane)及[显式编译面](engineering-module-surfaces.md#engineering-compiler-faces)落实。公开导出、依赖、局部测试导入和包README的详细义务仍由其专题拥有。

**目录的维护边界：**

| 路径或类别 | 必须保留的责任 |
|---|---|
| `apps/<app>/` | 配置、装配、启动和生命周期；业务规则留在能力包，通过声明入口或注册点接入，不变成CLI、gateway、manager或核心循环的业务分支总表。不同载体复用业务实现。 |
| `packages/<group>/<package>/` | 能力的实现、局部类型、合同、配置和测试一起维护；跨包用声明入口，不借根依赖或私有路径串成隐式模块。 |
| `packages/util/`、`packages/test-support/` | 分别拥有窄底层工具和真实共享测试基础设施；不能把无归属业务放进common/utils，也不为一次局部测试扩大公共导出。来源对新增包类别及静态库的限制仍归包形态专题。 |
| `packages/experimental/` | 实验能力与默认产品图隔离；搬入目录不自动完成隔离，也不等于有正式支持承诺。 |
| `scripts/` 与工具链配置 | 拥有检查、生成和仓库编排，写明入口及副作用；配置按语言原生位置维护，不在脚本中藏业务实现或复制另一份任务状态。 |
| `snapshots/`、`benchmarks/` | 前者保留会话驱动产品行为，其他预期输出归最低测试owner；后者拥有性能语料与门禁，不能用快照或基准替代彼此。详细覆盖归[测试策略](testing.md)。 |
| `vendor/` | 固定来源、本地修改和同步程序；不当成无人维护的拷贝。 |
| `native/`、`python/`、`website/` | 分别拥有真实原生实现、跨语言SDK/分发和网站投影；它们不是重复产品逻辑或第二份文档真源。 |
| 生成物、构建产物、运行态与秘密 | 明确输入、生成器、输出及freshness检查，源码检查与产物消费分开；用户数据、缓存、日志、秘密和私有维护状态不混入源码或默认分发，公开产品不依赖本机私有路径。必须交付的资源由分发清单明确拥有。 |

**工具链绑定不是自由改名。** 使用相同Node多包工具链的项目直接采用上述应用/能力族/包路径与包级 `tests/`；其他语言只有实际源码发现、构建或发布规则需要差异时，才绑定对应目录和原生配置。必须在架构/开发owner中写明源位置、目标位置、具体工具链原因及保留的职责和检查；不能只写“采用现有布局”或“项目较小”就豁免。业务能力名按真实项目替换，不创建来源的Agent功能包。只创建当前及本次需求确有对象的目录，不为占齐树生成空应用、空包或不存在的SDK；后续引入对象时按其固定归属建立。

文档、开发Skill及决策记录也是项目结构的一部分，但其完整目录和触发条件分别由本页开头链接的既有owner定义；不能拿上述代码树或共同标准的基础入口替代完整事实分类。移动代码同时追踪这些owner的相关事实和入站链接。

**完成条件：** 能从实际应用或库消费入口沿能力族README找到拥有包、包内源码和 `tests/`，包在真实workspace/编译/测试/打包图内；每处语言路径差异有真实工具链原因与等效检查，不靠目录存在或泛化职责判完成。

## 3. 模块边界、依赖与拆合

1. **先找已有职责，再决定新增模块。** 同一能力的局部变化在其模块内完成；不同职责独立演进、已有多种实现/消费者、不同部署或运行环境、独立发布合同需要隔离时再拆分。文件长短、层数对称和“以后可能替换”本身不是拆包依据。也不强制每个模块先有多个消费者；独立职责或真实发布合同同样可以成立。
2. **公开面小且真实。** 约定公开入口、输入/输出、错误、配置和生命周期；实现细节保持内部。跨包使用包名及声明入口，不能相对导入另一个包的私有源码；同包内部与测试可按工具链相对导入。依赖写入拥有包的manifest，不能借根依赖、提升安装或别名掩盖漏声明。
3. **依赖方向服从地图。** 消费者依赖能力合同，可替换实现依赖同一合同；装配层选择实现，业务模块不反向依赖装配入口。基础共享层不依赖具体业务。出现跨模块循环或双方互读私有实现时，重新判断职责、提取实际共同合同或合并同一关注点，不能只加转发导出隐藏关系；具体允许边、禁止边和必要例外在项目owner中明确并受审。
4. **扩展不污染中心。** 已有扩展点先复用，业务模块拥有并注册自己的行为；确需新seam时按[定义/实现/消费者](engineering-architecture-lifecycle.md#engineering-capability-seam)说明全部角色和运行装配，不为一次局部功能引入注册框架。多个独立运行环境/编译面按[模块平面](engineering-module-surfaces.md#engineering-compiler-faces)隔离。客户端多域和共享层另按[域图纪律](engineering-client-and-conversation.md#engineering-client-layering)执行，不能把它的具体 `contract/`、`apply.ts` 规定无条件扩成所有后端项目目录模板。
5. **每个包有真实角色。** 能从默认/明确可选入口使用，或明确是SDK、构建、测试、声明等受维护角色及理由；依赖已安装不等于实际被使用。可选实现未安装时的加载合同、实验默认隔离、共享实例身份等仍按专题落实。

对可机械检查的导入/导出、依赖声明、运行环境、产品可达性、生成图新鲜度及分发边界，接到项目真实检查/CI入口，观察正常、违规拒绝和恢复。语义归属、拆包必要性和地图含义由评审核对；不能用人工同意代替原本必需的机械阻断，也不能声称通用检查器能证明一切结构合理。

**完成条件：** 使用者从声明入口消费，不绕过私有实现；依赖声明和实际图一致，受约束的禁止边确实被拒绝；真实装配能运行，评审能解释为什么这样分而不是仅见到更多目录。

<a id="structure-evolution"></a>
## 4. 新建、扩展与迁移怎样保持结构

- **新项目：** 从第一条真实使用路径按§2建立应用、能力族和包内归属，确定允许依赖与装配点，架构地图随实现校正。没有对象不生成空层或虚构插件；“不预建无需求结构”也不允许把已有业务散放后不按规定归组。
- **新增功能：** 在动代码前确定拥有模块、对外合同和允许依赖；局部细节不改全仓规则，改变公共关系则同改地图和消费者。第二个真实需求出现时再评估共享或拆包，不机械复制第一份实现，也不因多一个调用就自动拆包。
- **已有项目改造：** 先从真实运行/库入口和实际导入图辨认当前职责，保全未提交内容、旧接口与数据。对混合模块、循环、私有跨包导入、孤儿、重复入口、源码/产物混用逐项指定目标归属、保持项和验证；可分切片，但每个切片完成实际切换，未迁移部分明确未落实。
- **移动、拆包、合包或删除：** 同步静态引用和动态装配、manifest/exports、工作区发现、构建/类型/测试图、配置及资源路径、文档链接、CI语料和打包白名单；重生成派生图/目录。检查现有用户内容后才清退被替代文件、旧声明和并行入口，不留下无人拥有的转发层。真实公共兼容承诺或数据升级按对应专题先做取舍和授权，不能以整理结构为由静默破坏。
- **验收：** 观察真实入口以及受影响源码检查和构建/安装消费者；确认没有依赖原位置、工作区偶然解析、私有缓存或旧产物才通过。再核对实际diff与地图、公开合同及文件职责，更新唯一状态；结构迁移不是只完成重命名或目录搬家。

**完成条件：** 新结构承担原职责，保持项仍成立，旧结构已退出，全部实际消费者和检查图已迁移；原失败保留，未验证层如实报告。无工具/权限时按[缺项与阻塞](project-standard.md#governance-status)处置，不把结构规范变成可选建议。
