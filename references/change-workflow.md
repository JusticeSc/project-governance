# 工程变更与 reconciliation

本产品维护及接入迁移中的工程变更使用本流程；交棒后的目标工程按自身AGENTS、文档和开发Skills持续开发，不经外部采用Skill路由。接入以[项目治理标准](project-standard.md#project-standard)的共同目标状态为规范，空项目建立与已有项目改造按[建立与改造流程](adoption.md#adoption)执行。本页拥有从需求到实际diff的操作顺序，领域细则归下列参考；执行规模随真实变更面选择，不为每个小改动创建文档、研究任务或新的状态体系。

## 1. 开工：核实事实与归属

读当前请求、既有需求和验收、项目指令、实际分支与完整工作树。区分基线已有内容、本次拟创建内容和之后必需的变更面；未提交、暂存和未跟踪内容都是需要核实的输入，不能因不在 HEAD 中而删除或覆盖。当前请求决定权限；旧下一动作、历史成功或归档提案不构成许可。

复用目标的需求、任务状态、长期决定、事故、程序和数据格式拥有者；记录缺少的归属，不先复制一套目录。需求/任务 owner 按[标准](project-standard.md#governance-owners)承载目标、范围、保持项、验收及证据；需跨会话的状态 owner 还须承载阶段、未决、一个可执行下一动作和接续合同。长期决定、事故、程序及数据格式 owner 按各自职责与生命周期判断合规，不要求承担当前任务状态。存在不等于合规，不合规处原位补齐或迁移。满足[状态启用条件](state-owner.md)且没有合规状态 owner 时建立唯一记录。安装位置 `.agents/skills/project-governance/` 存放程序和参考，不存项目的需求/进度；[`.agents/notes/`](agent-notes.md#1-激活与目录) 是长期理由触发时按生命周期落实的决策布局。

需要持久记录时，将本次结论写到既有任务/决定 owner，其他报告只链接；无需持久记录时留在当前交付。事实类别可以由同一文档的明确区域拥有，不能为了目录对称而虚构内容。同一长期决定更新现有 owner；内容会改变决策时新建取代关系而非把旧理由改成相反结论。Note 的目录、格式、迁移和冻结检查遵循[Note模块](agent-notes.md)，不因安装了模块就声称接入完成。

代码新增、重构或结构迁移前先读项目 `docs/architecture.md`，按[结构组织规范](project-structure.md#project-structure)定位拥有模块、公开入口、允许依赖和装配点；没有地图先补真实关系，不用目录名猜职责。本次若改变这些关系，同步地图、所属合同与检查/分发图，不因搬移后局部测试绿色就称切换完成。

**完成条件：** 请求、实际输入和权限可核对；状态/决策归属不竞争；未确认事实单列，不用拟议路径冒充已有事实。

## 2. 分析：从症状到可检验的修正

修复、简化或治理质量问题时，先描述可观察症状及影响：谁在什么条件下得到了什么错误结果，预期是什么，原证据在哪里。建立能区分正确和错误的最小反馈路径，保留已报告或已观察的失败，不为确认同一失败重复运行。

区分已知事实和因果假设。提出能被观察推翻的机制解释，再检查输入、状态、执行顺序、责任、依赖及检查的实际覆盖。历史决策、事故、测试和同类实现用于提出候选策略：说明相同的失败机制、不同前提和迁移限制，不能把类比或旧绿色结果当作当前证明。证据足以支持局部修正时进入实施；小问题无需写研究报告，也不必为凑备选方案发明抽象。

选择能保持真实需求和契约的最小方案。新增参数、包、缓存、重试、兼容分支或验证层都需对应已确认消费者、输入边界或失败机制；可删除无实际作用的重复，不靠猜测未来需求增加维护成本。检查只能执行其编码的谓词；必要性、适用性、复杂度与文案含义由具名评审承担。需要改变要求、降低保证或越过权限时先交回决定，不能把缺前提改写成不适用。

**完成条件：** 方案对应具体症状/要求和可反驳机制，新增复杂度有依据；未知、风险和所需决定已明确。

## 3. 影响分析：从需求反查义务

在改动前明确预期行为、必须保持的行为、预计路径及依据、生产者/消费者、数据/资源拥有者，以及正常、无效和兼容边界的验证入口。预计文件是影响假设，不是绝对白名单；公共符号用目标语言的引用/类型工具追静态调用者，动态拼装、外部消费者和真实装配另补入口证据。

先根据下表反查已知、拟新增和必需的变更面，再跟随[专题索引](index.md)发现其余依赖。表是检查方向，不是封闭义务清单，也不是要求每次加载全部领域正文。

| 检查方向 | 需要追问的影响 | 具体参考入口 |
|---|---|---|
| 类型与接口 | 哪些调用方、测试/脚本和示例依赖形状、错误、默认值或时序？静态图是否包含它们？ | [工程索引](engineering.md)、[检查选择](engineering-workflow.md#engineering-check-selection)、[源/产物平面](engineering-module-surfaces.md#engineering-source-artifact-plane) |
| 架构、依赖与生命周期 | 新代码属于哪个模块/目录，允许依赖谁，是否确需拆合，真实组合能否加载，谁注册/撤销/释放资源？ | [结构组织与演进](project-structure.md#project-structure)、[架构与生命周期](engineering-architecture-lifecycle.md)、[组合](engineering-runtime-composition.md)、[供应链](supply-chain.md) |
| 行为与回归 | 哪个外部结果能暴露错误，断言是否独立于实现，真实入口/隔离/平台前提是什么？ | [测试索引](testing.md)、[失败与信任](engineering-failure-and-trust.md) |
| 持久化与兼容 | 旧数据怎样读取，字段含义是否改变，恢复/回放是否复用同一权威规则？ | [当前记录](persistence-current-records.md)、[历史格式](persistence-historical-finalized.md)、[升级](upgrade-guides.md) |
| 文档与派生内容 | 哪些当地契约必须同步，谁生成派生内容，双语/链接/示例的实际语料是什么？ | [文档触发](documentation.md#reader-triggers)、[文本审查](prose-review.md#prose-review) |
| 构建与交付 | 源码检查是否依赖旧产物，实际包/安装消费者是否可用，声明了哪些平台能力？ | [包合同检索](cli.md#package-domains)、[供应链](supply-chain.md)、[发布](release.md) |
| 评审与协作 | 哪些规则需要人工接受，谁能改变检查，CI/审批/合并/历史操作分别有什么证据和权限？ | [评审](workflow-opening-and-review.md#aw-07)、[协作](collaboration.md)、[门禁接线](decisions.md#gate-wiring) |
| 持续开发支撑 | 当前事实/决定是否重复或被取代，简化删除保留了哪些义务，规则何时退出或重激活？ | [决定](decisions.md)、[简化](workflow-specialized-evidence.md#aw-18)、[规则退出](decisions.md#rule-retirement) |

对实际触发要求读取完整机制及对应小节，包括条件、依赖、例外和限制。将目标事实/位置连接到机制、目标参数、实施或评审责任、检查入口和状态。没有触发面才判不适用，并说明事实及再激活条件；触发后缺入口、语料、回归或接线属于未落实，应在当前权限内补齐，只有工具、依赖、事实或权限等前提不可达才是阻塞，须写明缺少什么、已尝试什么与解除条件。一个方向没有新义务时说明核对依据即可，不逐项抄写全部机制或固定来源参数。

空项目建立或已有项目改造必须先覆盖这些方向，并由评审从目标事实和原要求反查遗漏；日常开发复用确实满足[标准](project-standard.md#project-standard)的状态/决策 owner，只处理本次触发与发生变化的条件，不重新认证整体体系。来源编号和方法综合在产品仓库维护，目标项目直接使用随包机制和参考，不需要维护者工作空间或来源 checkout。

**完成条件：** 全部实际影响面和适用义务都有处置；预期改动、保持项、目标参数及验证可核对，未决没有被默认判绿。

## 4. 实施中：保持范围和证据有效

按标准、本次已复核的计划和既有验收实施，接口两侧、相关文档和派生产物同步。先更新拥有者，再重生成或更新消费者。观察真实行为并使用能发现当前回归的最小充分检查；CI 保留已声明广覆盖和平台矩阵，局部结果不冒充全量。

新事实需要修改预计范围时，在动作前评估新增义务、影响和权限。权限内必要的共享层修正可以调整计划，并保留原因；涉及风险或授权边界时先取得决定。新范围、基线或检查实现使旧证据失效时只补对应验证，不因换会话、提交或推送重复未失效检查。

测试断言应观察调用者/用户的状态或输出，并能因真实回归失败；不能让生成实现与生成测试互相复述成为唯一判据。可见文字或规定格式本身是契约时允许相应断言，但不以源码/作者报告的关键词命中替代实际行为。修改测试、检查、阈值、排除或期望结果也属于需要说明和独立评审的变更，不许通过删除失败判据、空语料、吞退出码或重录错误期望制造成功。规则替代/撤销按[退出流程](decisions.md#rule-retirement)。

**完成条件：** 请求行为完整实现，所有受影响消费者同步；范围变化有依据，验收保持有效，失败没有被压制。

<a id="reconciliation"></a>
## 5. 完成前：核对预期与实际 diff

使用实际基线、已提交/暂存/未暂存 diff 和未跟踪文件，分别核对两类偏差：该做却没做的调用方、兼容、文档和检查；以及额外引入的文件、依赖、抽象、行为、权限或规则变化。所有改动都在预计文件内也不证明合理；出现新文件也不自动等于越界。

每个差异判为原意图覆盖、依据新事实的合理调整、必须撤回的无关改动，或待决定的影响。把依据、影响与验证放在本次既有 owner/交付，不复制一份新的进度账。逐项检查真实语义与契约，尤其是被删除的能力、校验、异常传播和测试；仅比较路径数量或删除行数不够。

独立评审从原需求、机制和目标事实反查两侧：要求有没有遗漏，实际改动有没有无依据新增。审查者自己的误判也保留原稿和更正理由；不因第二个模型同意就判通过，也不把更正后的报告追认成首次验收。必需冲突、争议或阻塞未解决，不交付为完成。

**完成条件：** 实际全部变更及遗漏得到处置，必要性、范围、契约与证据一致；检查变化已接受，未解决项不隐藏。

## 6. 交付与冷接续

报告实际运行的命令、退出码、原输出和覆盖范围；复合命令只有总结果时不编造子结果。区分本地、真实 CI、平台保护和人工接受。新增/调整强制机制保留同入口的正常、真实拒绝、字节精确恢复证据；没有跑到检查的用法/配置失败不算该不变量被拒绝。持续回归留在项目真实入口，临时探针不能替代它。

启用状态时更新唯一owner的实际阶段、验收状态、原证据链接及一个下一动作；长期理由归决定拥有者。冷会话按当前请求、实际仓库、工程指令、目标owner、适用标准和已评审决定及原收据继续，重新判断新触发面，不能依赖上轮聊天或恢复已撤销任务。

**完成条件：** 每项必需验收有对应真实结果/评审，没有影响验收的未解决项；接续者不需要私有研究材料或临场提示。

## 依据与保证边界

本操作顺序是本产品的共同变更规范（目标迁移设计），整合随包工程、测试、文档、持久化、供应链、决定和协作机制；不是来源项目已有的通用状态协议。共同目标状态与固定职责归[项目治理标准](project-standard.md#project-standard)，空项目建立和已有项目改造步骤归[接入流程](adoption.md#adoption)。来源要求和范围见上述各拥有者，固定来源包括 `.agents/skills/dsh-pre-push-checks/SKILL.md`、`dsh-code-review/SKILL.md`、`dsh-find-simplifications/SKILL.md`、`.agents/notes/README.md` 与 `AGENTS.md`，许可见 [SOURCE-LICENSE.txt](../SOURCE-LICENSE.txt)。程序与评审只证明实际覆盖和观察的结果；本流程不保证 Agent 从不生成错误，也不将启发式命中定义为 AI slop。
