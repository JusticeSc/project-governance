# 按体系建立或改造项目

<a id="adoption"></a>

本页第2–7节提供单独开展项目治理改造时的深入参考，不是安装固定模板的前置门槛，也不要求每次安装重演历史实验。只需安装模板时，以[安装Skill](../SKILL.md)为入口；后续实际开发和维护由目标工程自身材料承接。

## 1. 安装模板与确定后续范围

<a id="adoption-scope"></a>

本产品随附的 Node.js/TypeScript 工程是当前固定模板。先确认目标项目的技术栈、路径和保护对象，再按[安装Skill](../SKILL.md)从目标项目外执行 `npm run install-template -- <项目目录>`。新目录和无冲突的已有目录可直接安装；有冲突时命令列出冲突并在写入前停止。需要合并已有文件时，先审阅实际内容并获得必要授权，再把模板实际接入项目根目录；独立参考树不是安装结果。

模板的环境、Git 初始化和示例业务替换见模板自身的[开发指南](../templates/node-typescript/docs/development.md)及[新项目教程](../templates/node-typescript/docs/cookbook/starting-a-project.md)。安装成功不代表依赖、业务替换或后续项目改造已完成；不为本次安装额外要求完整治理验收。用户另行要求既有项目深度改造时，才按实际范围使用以下章节并保留用户文件、业务与权限边界。

## 2. 绑定目标事实与差距

<a id="adoption-target-facts"></a>

核对标准所需的入口、代码/文档/任务/决定/历史各自归属，实际工具链、依赖、运行/消费/构建/测试入口、CI和权限。区分已经存在、本次拟建、后续必需的对象与未知；拟议路径不是实际能力。已有合规内容复用，缺项补齐，冲突迁移。

按[跨方法反查](change-workflow.md#obligation-sweep)追接口、架构/资源、行为、持久数据、文档/派生内容、交付、评审和持续开发支撑，再读触发专题及依赖。对相关要求确定实际owner、对象、命令/语料、实施或语义评审责任及验收方式；在任务或对应配置记录必要绑定，不把全部机制目录抄成新的规范。没有触发面的给出事实依据和重新触发条件，本次新增对象也在范围内。

按[缺项与阻塞](project-standard.md#governance-status)分别处理：可在权限内补齐的是工作，不先当作环境阻塞；工具/依赖/事实/权限不可达时保留准确阻塞，完成无依赖的可达部分。记录与正文冲突、无法在不削弱作用的前提下落实时，带具体原句、对象和影响交回维护者；必要未决不默认判绿。核对原要求的独立条件、依赖与例外，并反查每条新增解释有无事实或原要求支持，不能用引用、字段或计数代替语义核对。

**完成条件：** 每项实际差距有修改对象、保持项和验证，或明确的阻塞/未触发事实；工具、路径和参数有真实绑定，不用整体采用表的字段齐全替代判断。

## 3. 空项目：让第一条真实功能带起工程基础

<a id="adoption-empty"></a>

1. **定义行为与结构。** 明确真实使用者、输入/输出、错误及副作用，按[来源代码布局与工具链绑定](project-structure.md#structure-placement)确定应用、能力族、拥有包和包内源码/测试，说明允许依赖与装配点，形成架构地图并随实现校正。确定要保持的接口和数据合同；不为以后可能用到的功能预建分层、多包、注册框架、重试或兼容分支。完成时功能可判成败，新增代码有既定放置位置和关系，路径差异有具体工具链理由。
2. **建立可运行入口。** 配置实际依赖和脚本，完成一条用户运行或库消费者调用路径；构建型项目建立真实构建及产物消费路径。运行结果必须来自真实入口，不是替身或文案。完成时合法输入产生预期结果，非法输入在正确位置失败且无不应有的副作用。
3. **落实完整事实归属。** 建立[基础项目入口](project-standard.md#governance-owners)，并按[文档分层与完整事实映射](documentation-adoption-and-checks.md#migration)落实实际类别，不能只建立入口表中的文件。架构地图、组和包README各自维护其作用域，开发/测试页链接真实命令与职责owner。需要跨会话才建立缺失的状态载体；长期理由按[Note准入与目录](agent-notes.md#1-激活与目录)落实，不制造空Note或事故，不把生命周期正文复制进架构页。完成时下一位开发者可以找到项目、运行它并确定代码和事实应放在哪里。
4. **形成回归与检查。** 为真实契约的正常、错误及相关边界保留行为断言，按语言加入必要的类型/语法/导入和文档检查；断言观察结果，不固定无关实现文本。按[接线步骤](#adoption-wiring)建立共享定义和CI，验证第一条功能以及新增约束。完成时同一缺陷能被对应入口拒绝，合法情形仍通过。
5. **评审并交付。** 按[日常闭环](change-workflow.md#reconciliation)核对遗漏、额外复杂度、接口两侧、文档和证据，正常修正后复审；按[完成条件](#adoption-continuation)交付。CI或权限不可达就保留相应未完成层，不把仅本地通过当体系建成。

空项目无旧数据就不编造数据迁移；本次若引入持久化、双语、生成内容、包或平台，则必须同时落实其专题要求。第一条真实功能和工程基础共同交付，不先完成一轮治理认证才开始写业务。

## 4. 已有项目：保护业务契约，替换冲突制度

<a id="adoption-existing"></a>

1. **保全与建立可信基线。** 核对分支、已提交/暂存/未暂存/未跟踪内容，标明用户已有成果；识别真实使用者、接口、旧数据、资源及发布/安装路径。在不改变数据的条件下运行相关入口，保留已有失败及覆盖范围；用户报告的失败直接作为事实，不为确认重跑。没有可自动验证的关键契约时补最小行为基线，不能固定已知错误为正确预期。完成时可区分原有问题与本次引入问题。
2. **确定迁移对象与保持项。** 依§2比较标准，从真实入口和实际导入图按[结构改造规则](project-structure.md#structure-evolution)识别混合职责、私有跨包导入、孤儿与重复入口，以及缺失地图、重复状态、冲突规则和失效检查。已有owner只在符合各自职责、生命周期和证据要求时复用；不符则原位补齐或迁移。把目标模块/目录、允许依赖、迁移顺序、受影响引用和业务/数据保持项放进当前任务或真实设计决定。完成时每个冲突有唯一替代去向，不另举行整体接受治理认证。
3. **逐个完整切换。** 先保全原件和有效理由，再按[结构迁移的完整消费面](project-structure.md#structure-evolution)同步代码、动态装配、manifest/exports、构建/类型/测试图、资源路径、文档、CI语料和分发清单。新入口承担责任后清退旧文件及并行权威，必要历史退出执行；公共兼容承诺和数据升级按相应专题处置，不以搬目录为由破坏。长记录按职责拆分，不改写冻结历史、不覆盖用户未提交内容。切片可分批完成，未迁移义务仍明确未落实，不能以并存作为长期兼容方案。
4. **修接线而不损失保证。** 按§5复用已有工具和检查定义，补本体系所需的缺项；保留有效的业务断言、安装/构建依赖和支持平台。规则替换或缩窄须按[规则退出](decisions.md#rule-retirement)说明保证去向与代价，不能以接入治理为由删除原有保护。完成时新的错误会失败，旧保持项仍成立。
5. **完成真实变更与回归。** 用当前真实功能、修复或治理迁移需求执行[共同日常流程](change-workflow.md#change-workflow)，尤其追完整接口两侧、数据兼容、资源清理、文档和产物。持久格式变化按相关兼容/升级专题处理；破坏性转换必须先取得授权与可核对的数据保护方案。完成时原保持项与新行为同时有证据，原失败未被转绿或隐藏。
6. **评审及交付。** 核对实际完整diff与迁移前状态，确认旧制度已退出而业务没有无依据变化；再按§7报告。与本次验收无关的历史业务问题可另留归属，但本次已触发治理义务不能以“历史遗留”为由豁免。

## 5. 配置、共享检查与 CI 接线

<a id="adoption-wiring"></a>

准备固定依赖、真实完整受检语料和必要产物。项目脚本或配置是检查定义的owner，本地与CI复用规则和失败语义；接线验收运行覆盖全部已声明检查的入口，日常本地按完整diff选择最小充分集，CI保留广覆盖和支持平台。依赖产物的检查须先构建，共享资源/调度/取消也须避免漏跑后误报成功。

可直接使用项目已有顶层入口；使用本包聚合器时，清单只登记真实项目命令，例如 `{"checks":{"tests":"目标测试命令"}}`，以 `node <安装座>/apps/cli/bin/governance.mjs check <repo> --policy <仓内路径>`执行，将`<安装座>`替换为实际安装路径；省略策略路径时读取目标根的 `governance-checks.json`。清单不复制需求/进度，也不把顶层聚合器登记为自己的命令。所有策略路径须在目标真实仓库范围内，命令按实际shell权限执行，先确认依赖和副作用。

审查语料、排除、阈值、期望与工作流的实际diff。新增/修改机械约束观察§6的正常、目标违规拒绝和精确恢复；相关持续正常/无效断言进入真实共享入口，临时探针不替代回归，也不要求消费者复制整套检查器上游测试。语义义务由明确评审者核对。

本地Git hooks承担配置中有限的快速检查，不能替代开发者相关验证或CI；CI步骤必须传播非零，必需失败、取消或跳过不能汇总成功。平台负责人在受权范围配置和观察required checks/审批，执行者不因选择体系就获得远端保护设置权限。

**完成条件：** 真实共享入口可运行，检查对象完整、失败传播正确，持续回归和评审责任到位；CI实际运行、平台实际强制分别有对应结果，缺哪层就如实未完成，不能把工作流文件或聚合器退出0当作全部保证。

## 6. 正常、拒绝与精确恢复证据

<a id="adoption-receipts"></a>

对本次新增或修改的检查接线，从同一真实入口观察正常通过、真实破坏目标义务后非零拒绝、精确恢复后通过；合法近似仍通过。配置用法错误或缺依赖的退出不是目标违规被拒绝。没有改变的有效结果按身份与范围复用，不要求每次普通功能任务重演所有门禁。

在受权scratch范围或隔离副本中执行破坏与恢复，不污染用户数据；保存原始stdout/stderr、实际退出码、相关文件身份及注入/恢复动作，日志不含秘密。证据归当前任务已有位置，记录只链接原输出；临时文件清理前保留必要收据。报告数值与诊断从原观察引用，不靠回忆补出编码、文件或覆盖结论。

本地执行、CI运行、平台强制和人工评审分别记录。缺外部环境或权限就写清阻塞、影响和解阻动作，不用静态配置推定实测，不通过放宽规则制造绿色。

**完成条件：** 目标违规确实到达并触发对应检查，恢复后相关字节与注入前一致；原输出和覆盖层可核对，清理后证据仍存在。没有改变的新约束不虚构拒绝实验，语义review不冒充自动证明。

## 7. 达标与交棒

<a id="adoption-continuation"></a>

空项目或已有项目完成建立/改造，必须同时满足[共同目标状态](project-standard.md#governance-status)：真实需求完成，全部已触发规范落实，迁移保持项成立，验证与review完成，没有影响本次验收的未落实、阻塞或争议。单个工具、目录、元数据、记录或安装成功不构成采用完成。

交付包含实际变更、已清退旧入口、运行命令和退出状态、原输出、评审处置及明确未验证面；已有工程的迁移记录还应绑定迁移前基线、保持项、迁入后的实际owner及首次共同验证结果，复用当前任务记录，不另建采用账本。保留原失败，事后修报告不追认原结果。涉及集成、合并、发布按各自权限和真实状态，不能从本地通过推断远端完成。

需要接续时更新唯一状态owner的事实、证据、未决和一个可执行下一动作。新会话从当前请求、实际仓库、项目入口和原证据继续，重新判断新增触发面；不依赖前一聊天、私有研究或已经退出的旧决定。首次建立／迁移验收与记录完成后退出采用流程；之后每次变更从工程自身AGENTS、开发／测试文档及项目内Skills维护同一标准，发现缺项修正，重要理由按生命周期更新，冻结历史保持不变。

**完成条件：** 行为和规范各有对应证据，已有工程的迁移保持项与首次共同验证可核对；后续开发者能从项目自身找到并执行实际入口、必要规则、Skills与检查，安装座不承担第二日常owner。仍影响本次接入验收的缺项明确未完成并指向owner；没有把“接受体系”再次变成额外签字门槛，也没有把正常工程review取消。
